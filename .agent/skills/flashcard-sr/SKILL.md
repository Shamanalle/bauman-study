# Flashcard + Spaced Repetition Engine

Реализация полноценного режима Flashcard с движком интервального повторения (SR)
для платформы `bauman-study`.

> ### 🎯 Миссия
>
> Ты создаёшь **систему обучения**, по которой студенты МГТУ им. Баумана будут
> по-настоящему запоминать определения, теоремы и формулы. Текущий справочник
> позволяет **прочитать** — но не запомнить. Студент думает, что выучил,
> а на экзамене не может вспомнить.
>
> Flashcard-режим решает именно эту проблему через два научных принципа:
> **active recall** (активное припоминание) и **spaced repetition** (интервальное повторение).
>
> **Твоя задача — не просто реализовать фичу, а придумать максимально
> качественную реализацию для этого конкретного контекста.** Ты знаешь предметы,
> знаешь структуру вопросов, знаешь как студенты готовятся. Используй это.

## 1. Контекст проекта

### 1.1 Что это за проект

Платформа — **SPA на vanilla JS** (Vite сборка), работает **полностью offline**.
Данные — JSON-файлы. Прогресс — `localStorage`. Никакого сервера.

### 1.2 Твои инструменты (изучи перед началом)

Прежде чем проектировать что-либо, **обязательно прочитай** эти файлы:

| Файл | Зачем читать |
|------|-------------|
| `src/js/app.js` | Как устроен роутинг, как подключаются режимы |
| `src/js/data-loader.js` | Как загружаются JSON-данные, структура `{ meta, sections }` |
| `src/js/progress.js` | Как хранится прогресс в localStorage, `setPrefix()` |
| `src/js/question-card.js` | `buildQuestionBody()` — **переиспользуй** для рендера карточки |
| `src/js/renderer.js` | Как устроен текущий справочный режим |
| `src/js/text-utils.js` | `nl()` — преобразование markdown→HTML |
| `src/js/math-utils.js` | `renderMath()` — рендеринг KaTeX |
| `src/css/base.css` | CSS-переменные (цвета, шрифты) |
| `src/css/dark.css` | Тёмная тема — добавь overrides |
| `src/index.html` | Текущая разметка |

### 1.3 Данные, с которыми работаешь

Посмотри несколько реальных JSON-файлов разных предметов (физика, ЛА, АЯ, ИиДУ).
Каждая карточка содержит поля, из которых можно строить flashcard:

- **`title`** — название (вопрос)
- **`type`** — тип (Определение, Теорема, Понятие, Закон, Формула + вывод)
- **`formalText`** — полный формальный текст (что пишут на контрольной)
- **`formula`** — ключевая формула (KaTeX, без `$$`)
- **`insight`** — объяснение простыми словами
- **`note`** — уточнение, нюанс
- **`steps`** — пошаговое доказательство/вывод
- **`example`** — числовой пример

Разные предметы имеют разный баланс этих полей. Физика — много формул и доказательств.
АЯ (C++) — код, понятия. ЛА — формальные определения и теоремы. Подумай,
как flashcard-режим может это учитывать.

## 2. Что нужно реализовать

### 2.1 Spaced Repetition движок

Реализуй движок интервального повторения на основе **алгоритма SM-2** (как в Anki).
Данные каждой карточки хранятся в localStorage. Ключевые возможности:

- Отслеживание состояния каждой карточки (знание, интервал, множитель)
- Определение, какие карточки пора повторять (`due`)
- Определение новых карточек (ещё не видел)
- Сборка сессии из подходящих карточек
- Статистика: выучено / на повторении / новых

Важно: движок должен быть **отдельным модулем** (чистая логика, без UI),
чтобы его можно было переиспользовать в будущем для других режимов (quiz, экзамен-симулятор).

### 2.2 Flashcard UI

Режим интегрируется в существующую платформу (не отдельная страница).
Студент должен иметь возможность переключиться на flashcard-режим из текущего бандла.

Сессия flashcard включает три фазы:
1. **Настройка** — выбрать, какие карточки повторять, сколько
2. **Сессия** — карточки по одной: вопрос → (подсказка?) → ответ → самооценка
3. **Результаты** — итог сессии, что повторить

**Самооценка** — ключевой механизм. Студент оценивает, насколько хорошо знал ответ.
Это питает SR-движок. Достаточно 3 уровня оценки (не знаю / помню / легко),
но ты можешь придумать лучше, если обоснуешь.

**Горячие клавиши** обязательны — студент, который прогоняет 20 карточек,
не хочет каждый раз тянуться к мышке.

### 2.3 Ограничения

- **Vanilla JS** — никаких фреймворков
- **ES modules** — как в остальном проекте
- **Offline** — только localStorage, никаких сетевых запросов
- **Переиспользуй** `buildQuestionBody()` для рендера ответа карточки,
  `renderMath()` для KaTeX, `nl()` для markdown
- **CSS-переменные** из `base.css` — не хардкодь цвета
- **Dark theme** — обязательна (добавь overrides в `dark.css`)
- **Мобильный UX** — кнопки достаточно крупные, всё читаемо на 320px

## 3. Как думать (творческая свобода)

У тебя есть полная творческая свобода в проектировании UI/UX.
Вот **вопросы**, над которыми стоит подумать — не инструкции, а пища для размышлений:

### Про UX

- Как студент попадает в flashcard-режим? Таб? Кнопка? URL-параметр?
  Что самое естественное для текущего интерфейса?
- Как выглядит «лицевая сторона» карточки? Только title?
  Или для теоремы стоит показать формулировку, а скрыть доказательство?
  А для определения — скрыть formalText? Подумай, что именно студент
  должен **вспомнить** для каждого типа карточки.
- Нужна ли анимация «переворота» карточки? Или это отвлекает?
- Как показать прогресс сессии, чтобы студент чувствовал движение вперёд?
- Что если студент хочет повторить только определения? Или только формулы?
  Насколько гранулярной должна быть фильтрация?

### Про SR

- Оптимальный размер сессии — 10? 15? 20? Зависит ли от количества карточек в бандле?
- Что если все карточки новые (первый визит)? Сколько новых показывать за сессию?
- Что если все карточки выучены? Как это отобразить, чтобы мотивировать?
- Стоит ли показывать дату следующего повторения?

### Про разные предметы

- Определение по физике и понятие по C++ — одинаковый формат flashcard?
  Или стоит адаптировать под тип контента?
- Теорема с длинным доказательством (steps) — как это работает в flashcard?
  Студент должен вспомнить все шаги? Или достаточно формулировки?
- Формулы — может, стоит отдельный режим «вспомни формулу» (показать title,
  скрыть formula)?

**Ты не обязан отвечать на все эти вопросы явно.** Они нужны, чтобы ты подумал
о контексте и принял обоснованные решения. Если у тебя есть идея лучше —
реализуй её.

## 4. Итеративный цикл самоулучшения

> **Это самая важная часть скилла.**
>
> Не сдавай работу после первой реализации. Ты не знаешь заранее, какая реализация
> будет лучшей — ты узнаешь это только увидев результат. Поэтому after каждого
> «вроде готово» ты запускаешь ревизию.

### 4.1 Цикл

```
iteration = 0

while (true) {
  iteration++
  
  // ── РЕАЛИЗАЦИЯ (или исправление) ──
  if (iteration == 1) {
    Полная реализация: SR-движок → UI → стили → интеграция
  } else {
    Применить улучшения найденные на предыдущей итерации
  }
  
  // ── ВЕРИФИКАЦИЯ ──
  npm run build → должно быть 0 ошибок
  Открой в браузере → проверь визуально ВСЕ экраны
  Пройди полную сессию как студент (5-10 карточек)
  Проверь dark theme
  Проверь edge-cases (пустой бандл, первый визит, всё выучено)
  
  // ── РЕФЛЕКСИЯ ──
  Задай себе вопросы по 5 осям:
  
  1. КОНТЕНТ — ПРАВИЛЬНО ЛИ ОТОБРАЖАЕТСЯ?
     Открой flashcard для нескольких разных предметов и типов карточек.
     - Формулы (KaTeX) — рендерятся корректно? Не сломаны? Не обрезаны?
     - formalText — отображается полностью, markdown работает?
     - Код (для АЯ C++) — подсветка, читаемость?
     - Steps (доказательства) — шаги видны, формулы в math рендерятся?
     - Контент соответствует действительности — то, что студент видит на
       «лицевой стороне», это действительно то, что он должен вспомнить?
       А то, что на «обратной» — это действительно полный ответ?
     
     Проверь конкретно: открой физику (формулы + доказательства),
     линалг (определения), АЯ (код + понятия). Не проверяй на одном предмете.
  
  2. ПЕДАГОГИКА — ЭТО ЛУЧШИЙ ВАРИАНТ ДЛЯ ОБУЧЕНИЯ?
     Это КЛЮЧЕВАЯ проверка. Встань на место студента перед экзаменом.
     - Помогает ли мой интерфейс **реально запомнить** материал?
     - То, что я прошу студента «вспомнить» — это то, что спросят на экзамене?
     - Самооценка — удобна и честна? Студент не будет жать «Легко» на всё?
     - SR-логика — интервалы разумные? Карточки возвращаются вовремя?
     - Формат flashcard подходит для ВСЕХ типов контента?
       Определение — ок. А теорема с 5-шаговым доказательством — тоже?
       Если нет — может нужен другой подход для теорем?
     - **Есть ли способ сделать обучение эффективнее?**
       Может, стоит показывать формулу отдельно от определения?
       Может, группировать связанные карточки?
       Может, добавить «last chance» перед результатами для ошибок?
     
     Если ты чувствуешь, что текущий вариант «ок, но не wow» — это сигнал
     к улучшению. Wow — это когда студент скажет «блин, удобно, хочу ещё».
  
  3. ЛАКОНИЧНОСТЬ — НЕТ ЛИ ЛИШНЕГО?
     - Интерфейс чистый и понятный? Или перегружен элементами?
     - Каждый элемент на экране несёт смысл? Убери всё, что не помогает.
     - Путь от «открыл бандл» до «начал повторять» — минимальный?
     - Нет ли лишних кликов, лишних экранов, лишнего текста?
     - Визуально — это выглядит аккуратно и современно?
       Или как студенческая курсовая из 2015?
  
  4. ФУНКЦИОНАЛЬНОСТЬ
     - SR сохраняется между сессиями?
     - Горячие клавиши работают?
     - Dark theme — всё видно, цвета не сливаются?
     - Edge-cases: пустой бандл, первый визит, всё выучено?
  
  5. КОД
     - Не дублирую ли существующие модули?
     - CSS через переменные, без хардкода?
     - Модули чистые?
  
  // ── РЕШЕНИЕ ──
  // Ответь себе честно на один вопрос:
  // «Это лучшее, что я могу сделать?»
  //
  // Не «работает ли?» — а «ЭТО ЛУЧШЕЕ?»
  //
  // Если есть хоть тень сомнения — значит, можно лучше.
  
  if (нашёл проблему ИЛИ нашёл стоящее улучшение ИЛИ не уверен что это лучший вариант) {
    Запиши что именно улучшить и почему → continue
  } else {
    // Финальная проверка: перечитай весь код с чистой головой.
    // Открой браузер ещё раз. Пройди 3-5 карточек.
    // Если и после этого ничего — заканчивай.
    break
  }
}
```

### 4.2 Примеры того, что находишь на ревизии

Это не чеклист — это примеры из реальных ревизий, чтобы ты понимал глубину:

**Контент:**
- «Формула $\int_a^b f(x)\,dx$ обрезается на мобильном → нужно scroll на math-box»
- «У карточки АЯ C++ в formalText код не подсвечивается → проверю что nl() обрабатывает pre/code»
- «На лицевой стороне показываю только title, но для «Формула + вывод» студент не знает
   КАКУЮ формулу вспоминать → нужно показать title + hint на формулу»

**Педагогика:**
- «Сейчас для теоремы прошу вспомнить формулировку, но на экзамене спрашивают
   и доказательство → может разбить на 2 flashcard: формулировка + доказательство?»
- «Студент жмёт «Помню» даже когда вспомнил неточно — добавлю на reveal-экране
   визуальное сравнение «вот что нужно было сказать», чтобы помочь оценить честно»
- «Сессия из 20 карточек — студент устаёт к 15-й. Может, лучше 10 по умолчанию?»

**Лаконичность:**
- «На setup-экране 6 кнопок — перегруз. Оставлю 2 главных + шестерёнку для настроек»
- «Лишний текст «Нажмите кнопку для начала» — студент и так видит кнопку»
- «Progress bar + текстовый счётчик + процент — избыточно. Хватит двух из трёх»

### 4.3 Когда заканчивать

Заканчивай **только** когда:

1. `npm run build` — 0 ошибок
2. Ты прошёл полную сессию в браузере (несколько предметов)
3. Контент отображается корректно для всех типов карточек
4. Ты уверен, что **этот вариант — лучший для обучения студента**,
   и не можешь придумать, как сделать его педагогически эффективнее
5. Интерфейс лаконичен — ничего лишнего
6. На последней итерации ты **честно** не нашёл ничего

Если сомневаешься — сделай ещё одну итерацию. Итерации бесплатны. Качество — нет.

## 5. Антипаттерны (красные флаги)

Если ты замечаешь любой из этих паттернов — остановись и подумай:

- ❌ Скопировал HTML-построение карточки вместо `import { buildQuestionBody }`
- ❌ Хардкодишь цвета (`#ff0000`) вместо CSS-переменных (`var(--accent)`)
- ❌ Не вызываешь `renderMath()` после вставки HTML с формулами
- ❌ Забыл про `progress.setPrefix()` — SR-данные перемешаются между бандлами
- ❌ Сессия по умолчанию из 100 карточек — студент устанет после 15
- ❌ Нет анимаций вообще — интерфейс кажется «мёртвым»
- ❌ Не работает на мобильном — кнопки мелкие, текст обрезается
- ❌ «Готово!» после первой реализации без единой ревизии
