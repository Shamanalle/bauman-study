1. 
Заголовки и файлы с исходным кодом 
Ещё в конце прошлого семестра вы начали сталкиваться с тем, что коды стали весьма 
внушительной длины, и ориентироваться с ними стало сложно. На этом месте пора переходить 
к программам, состоящим из нескольких файлов. 
Когда появляются классы, их принято выносить в отдельные файлы. На это есть 
несколько причин: 
1) классы могут быть объёмны и могут затруднять ориентирование в основном коде 
программы; 
2) классы являются обособленными единицами и не зависят от кода основной 
программы; 
3) классы могут использоваться не только в файле с основной программной, но и в 
файлах с описанием других классов. 
Причина № 3, кроме вынесения класса из основного файла, приводит к разделению кода 
класса на 2 файла: 
1) файл с объявлением класса его методов – заголовочный файл («хедер», header) – 
файл с расширением .h (иногда .hpp или .h++) 
2) файл с определением методов класса – файл с исходным кодом («сорс», source) – 
файл с расширением .cpp (иногда .c++) 
Расширения .h у вас, несомненно уже всплывали, некоторые из вас в прошлом семестре 
даже подключали устаревшие заголовки библиотек, пришедших из языка С в С++, которые 
имели это расширение. 
Аналогичным образом с помощью директивы #include мы будет подключать и 
заголовочные файлы наших классов, только с одной небольшой поправкой – вместо 
треугольных скобок (< и >) будут использоваться кавычки. Это говорит о том, что 
подключается пользовательский файл, который не стоит искать в местах расположения 
стандартных библиотек. 
На данном этапе рекомендую создавать файлы через интерфейс вашей среды 
разработки. В этом случае они будут добавляться в конфигурацию и не будет проблем при 
сборке.   
Что же должно содержаться в заголовочном файле? В первую очередь надо обратить 
внимание на защиту от повторного «подключения» файла. Вы же помните, что директива 
#include просто копирует содержимое подключаемого файла? Есть 2 способа защитить файл от 
повторного подключения: 
1) использовать header guards – набор директив препроцессора для условной 
компиляции. Тогда файл будет начинаться с #ifndef UNIQUE_CODE_NAME, 
где на месте  UNIQUE_CODE_NAME должно стоять некоторое уникальное имя,

следующей строкой – #define UNIQUE_CODE_NAME, а последней строкой – 
#endif. Работает буквально следующим образом: если не объявлен 
идентификатор UNIQUE_CODE_NAME, то он объявляется вместе со следующим 
за ним кодом до директивы #endif. 
2) Использовать директиву #pragma. Тогда первой строкой в файле указывается 
#pragma once, и на этом особенности заканчиваются. 
В каждом заголовочном файле должна быть защита в соответствии с одним из 
вариантов выше. 
Плюс первого варианта – это стандарт. Минус – надо придумывать уникальное имя, 
чтобы не было коллизий (обычно используется имя файла с _H на конце). 
Плюс второго варианта – простота, не нужно ничего придумывать. Минус – не входит в 
стандарт С++, но поддерживается большинством компиляторов. И, пожалуй, это единственный 
раз, когда я могу порекомендовать нестандартщину. 
Итак, в хедер выносится объявление класса с объявлениями (прототипами функций). В 
прототипах функций можно опускать названия параметров, оставляя только их типы, но я не 
рекомендую этого делать. Кроме того, в хедере могут быть определены маленькие функции – 
например, геттеры и сеттеры. В примере 1 приведено содержание заголовочного файла для 
класса Matrix. Для простоты ориентирования названия файлов, в которых описан класс, обычно 
совпадают c названием класса.

Matrix::Matrix(const Matrix &matrix) : n(matrix.n), m(matrix.m) 
{

{

for (int i = 0; i < n; ++i)

// транспонирование матрицы 
Matrix Matrix::transpose() 
{ 
 
Matrix newMatrix(m, n); 
 
newMatrix.values = new float*[m]; 
 
for (size_t i = 0; i < m; ++i) 
 
{ 
 
 
newMatrix.values[i] = new float[n]; 
 
 
for (size_t j = 0; j < n; ++j) 
 
 
 
newMatrix.values[i][j] = values[j][i]; 
 
} 
 
return newMatrix; 
}

{ 
 
if ((n_ > 0) && (m_ > 0) && (values == nullptr)) 
 
{ 
 
 
n = n_; 
 
 
m = m_; 
 
} 
}

2. 
Почему многофайловые программы – это хорошо 
Для пользующихся средами разработки процесс компиляции невидим, но он есть и для 
больших проектов он достаточно трудоёмок. Разбиение программы на отдельные файлы с 
исходным кодом позволяет отдельно компилировать только те части проекта, в которые были 
внесены изменения. 
Обращаю внимание, что это справедливо для файлов с исходным кодом (.cpp, .c++), т.к. 
именно они превращаются в объектные и подвергаются линковке. Вынесение части кода в 
заголовочный файл даст вам только сокращение размера основного файла с исходным кодом, 
и больше никакой практической пользы. 
Поэтому если вы работаете с составной программой, в которой много функций, но 
изменения в которых происходят редко, выносите их объявления в заголовочный файл, а 
определения (реализации) – в отдельный файл с исходным кодом. 
3. 
Предварительно скомпилированные заголовки 
 Некоторые из вас, вероятно, уже сталкивались с тем, что при создании непустых 
проектов среда разработки иногда требовала подключение странного пустого файла «stdafx.h» 
или «pch.h». Это предварительно скомпилированные заголовки – заголовочные файлы, которые 
были предварительно обработаны для оптимизации их использования при компиляции. В 
предварительно скомпилированные заголовки можно поместить те заголовки, которые 
меняются редко (и, соответственно, перекомпилировать каждый раз, когда они меняются) или 
не меняются вообще. Хороший пример последних – это заголовочные файлы стандартной 
библиотеки, которые вы точно ни разу за последний семестр не меняли  
Подключать предварительно скомпилированные заголовки нужно там, где они вам 
нужны. Если такой заголовок нужен только основном файле проекта (где main), то 
подключайте только там. Если те же заголовки нужны вам в других файлах проекта, 
подключайте и там.  
Зачастую в разных файлах требуются разный набор библиотек. Универсального 
решения здесь нет, всегда есть 2 стула: 
1) включать все библиотеки, делая избыточным для отдельно взятого файла 
исходного кода и тем самым увеличивая его размер; 
2) включать только общие библиотеки, а несовпадающие подключать отдельно. 
Какой из вариантов в отдельно взятом случае будет работать быстрее, зависит от 
случая. 
Будьте внимательны! Использование или не использование предварительно 
откомпилированного заголовка – это настройка компилятора для каждого файла с 
исходным кодом. Если использование предварительно откомпилированного заголовка
